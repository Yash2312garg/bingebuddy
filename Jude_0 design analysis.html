01 // OVERVIEW

What the DSA evaluation module is responsible for — and why it's hard

The evaluation module sits downstream of question authoring and upstream of the score card. Its job sounds simple: run code, check output. But every step carries subtlety — correctness, security, fairness, latency, and reliability must all be preserved simultaneously. This section explains the problem space before diving into the design.

Why is this harder than it looks?

Evaluating code is fundamentally different from evaluating a form submission or a database query. You are running arbitrary, untrusted programs from candidates you know nothing about. The program can contain infinite loops, gigabytes of output, fork bombs, network calls, file system writes, or attempts to read environment variables. It may be written in languages with entirely different runtime semantics. It may produce numerically correct output with different formatting. All of this must be handled correctly, fairly, and in under 30 seconds — while streaming live progress to the candidate's browser.

That is why the design has 8 stages, 11 known pain points, and a dedicated execution sandbox (Judge0) instead of a naive exec() call.

Why Judge0 and not a custom Docker sandbox? Judge0 provides a hardened isolate sandbox with per-process cgroup limits, battle-tested across 20+ languages, and a well-understood batch API. Building an equivalent from scratch would take months and introduce new security surface. The trade-off is vendor coupling and the CVE exposure documented in Section 10 — both manageable with the hardening checklist.

ℹ

Why BullMQ and not synchronous execution? A DSA submission with 20 hidden test cases can take 10–30 seconds to fully grade. An HTTP connection that holds open for 30 seconds per candidate is not scalable — it blocks a Node.js event loop thread and any upstream reverse proxy timeout will kill it. BullMQ decouples the HTTP response (instant 202) from the grading work, allowing the API to serve thousands of candidates simultaneously while a pool of dedicated worker processes handles the heavy lifting in the background.

02 // DESIGN CONSIDERATIONS

Every factor accounted for — the full problem space

Before writing a single line of code, a well-designed system enumerates all the forces shaping it. These are the constraints, invariants, and edge cases that drove every decision in this design. Missing any of them produces bugs that are hard to trace back to root cause.

A — Correctness considerations
C1
Output normalisation must be custom
WHY

Judge0's built-in expected_output comparison is a raw byte-for-byte string match. It fails on trailing spaces that print functions often emit, Windows-style \r\n line endings from Java/Windows programs, float precision differences (0.999999 vs 1.0), and case sensitivity. A correct solution would receive WA for cosmetic reasons.

WHAT

All output comparison happens in the grading worker using a multi-step normalisation chain. expected_output in the Judge0 payload is always set to null — we never let Judge0 compare. The worker fetches both actual and expected, normalises both identically, then compares. This is detailed in Section 07.

C2
Driver merge strategy is language-specific
WHY

Languages have fundamentally different file-level structure. Python: no entry point — just append the driver after the class. Java: multi-class files are legal — append a second Main class. C++: includes must be at the top — you cannot append includes to the bottom of a file. JavaScript (Node): module exports differ from global functions. A generic string-concat merger silently produces invalid code in every language except Python.

WHAT

The merger uses a strategy map: { language_id: MergeStrategy }. Each strategy implements a merge(starterCode, hiddenDriver): string interface differently. Adding a new language means registering a new strategy. Missing strategy → explicit error, not silent broken code. Detailed in Section 05.

C3
CE must halt all remaining test dispatches
WHY

If a candidate's code has a compile error, it will compile-error on every test case — not just the first. Dispatching all 20 test cases to Judge0 when the first one returns CE wastes 19 execution slots and delays feedback for other candidates queued behind. There is zero information gained by running the other 19.

WHAT

On detecting Judge0 status_id=6 (CE) during result processing, the worker immediately marks all remaining test results as CE with 0 points without making additional API calls. The compiler's stderr is extracted and sent to the candidate as the full error message. Session status moves to complete immediately.

RISK

In batch mode, all tests are dispatched simultaneously — you cannot cancel already-submitted Judge0 tokens. The CE halt prevents processing remaining results, not their execution. This is accepted and flagged as P3 in the pain points section.

C4
Test case fetching is server-side only
WHY

If hidden test case inputs or expected outputs ever reach the client — even in an API response field that's "not shown" in the UI — a determined candidate can inspect network traffic (Chrome DevTools, Wireshark) and use those inputs to craft solutions that pass without implementing the correct algorithm. The leakage doesn't need to be visible in the UI to be exploitable.

WHAT

The grading worker fetches test cases directly from the DB/S3 within the internal network. The candidate-facing API serialisation layer must exclude is_hidden=true test cases entirely — not just their expected output, but the test entries themselves. The is_sample flag controls which tests are shown in Run mode results.

B — Reliability & resiliency considerations
R1
Idempotency guard prevents double-grading
WHY

BullMQ uses at-least-once delivery semantics: if a worker crashes while processing a job, BullMQ retries the job. Without an idempotency check, the second execution writes duplicate dsa_test_results rows and the score aggregation sees 2× points for every test. The candidate gets a score above their max.

WHAT

At the start of every job, the worker checks: SELECT status FROM sessions WHERE id = $session_id. If status is already 'grading' or 'complete', the job exits immediately. The transition to 'grading' must be atomic (UPDATE with WHERE clause checking prior state) to prevent two workers racing to start the same job.

R2
Async pipeline decouples API from execution latency
WHY

A DSA submission with 20 hidden test cases, each running a Python solution at 3× time multiplier with 2s base limit, could take up to 60 seconds in the worst case. No sane HTTP timeout allows 60 seconds. Beyond timeout, a long-lived HTTP connection blocks a thread, increases memory pressure, and is vulnerable to network disruption.

WHAT

The API returns 202 Accepted in under 50ms. The job is enqueued to BullMQ. The candidate's browser holds an SSE connection to receive progress updates as the worker processes each test. The HTTP request that triggered the grading is already closed by the time the first test result arrives.

R3
Judge0 polling must have timeout + backoff
WHY

Judge0 queues submissions internally. Under load, a submission may sit in queue for 1–3 seconds before execution begins. If the worker polls at fixed 400ms intervals and Judge0 is processing 200 concurrent submissions, it generates 500 polling requests per second — a self-inflicted DDoS on the execution cluster. Worse, if Judge0 goes down, the worker spins polling forever.

WHAT

Exponential backoff: first poll at 400ms, then multiply by 1.5× each round, capped at 2000ms. Hard timeout at 30 seconds — after which the job fails and the candidate receives a system error. The backoff diagram below illustrates the polling curve.

R4
Session state machine must be explicit
WHY

Without an explicit state machine, every part of the codebase that touches a session must re-derive what states are valid. This leads to inconsistencies: e.g., the cleanup job marks sessions as expired while the worker is simultaneously marking them complete, or a candidate re-submits after grading because the front-end didn't receive the lock signal.

WHAT

The sessions.status column is the single source of truth. The valid FSM is defined below. Any database write that changes status must specify the expected prior state in the WHERE clause (optimistic locking), so concurrent writes fail loudly rather than silently corrupting state.

ℹ

Grading → complete must be an atomic transition. The worker sets status to grading BEFORE dispatching to Judge0. C — Security considerations
S1 — Judge0 CVE exposure

Judge0 ≤v1.13.0 has three critical CVEs (CVSS 9.1–10.0) enabling sandbox escape to root via symlink attacks and SSRF to internal PostgreSQL. The attack vector: a candidate submits code that exploits the isolate sandbox escape, gains access to the Judge0 host filesystem, and reads internal credentials from environment variables.

Patched in v1.13.1+, but the hardening checklist (network disabled, changed passwords, internal-only port, resource limits) is mandatory regardless of version. See Section 10 for the full checklist.

S2 — Judge0 network isolation is non-negotiable

If a candidate's code can reach the network, it can exfiltrate hidden test case data (by calling back to a server they control), probe internal services (SSRF), or perform outbound attacks during an exam. enable_network: false must be set on every batch submission payload — not as a Judge0 default, but explicitly in every API call so a misconfiguration doesn't silently re-enable it.

S3 — Hidden driver must never reach the client

If a candidate sees the hidden driver code, they can learn the exact input format and write a solution that hardcodes the expected output for each test case rather than implementing the algorithm. The driver is in dsa_language_stubs.hidden_driver and must be excluded from every API serialisation — not just the candidate endpoint but any admin endpoint that might be discovered.

S4 — Code size and output limits must be enforced

A candidate can attempt to crash the grader by: (1) submitting a 10MB source file — exhausting API memory during parsing, (2) writing an infinite output loop — filling Judge0's stdout buffer and eventually causing OOM, (3) submitting a fork bomb — exhausting process table. All three vectors must be stopped before reaching Judge0: code size cap at the API layer (50KB), stdout cap in Judge0 config (1MB), process limit via cgroups.

D — Fairness & scoring considerations
F1 — Language execution time differs — multipliers needed

The same algorithm implemented in Python vs C++ can differ by 3–5× in execution time on identical hardware. A flat 2-second time limit would systematically TLE every Python solution that would pass in C++. The time_multiplier column in dsa_language_stubs adjusts the per-language limit: cpu_time_limit = base_limit × multiplier. Python gets 3×, C++ gets 1×.

The table in Section 06 gives reference multipliers, but they must be empirically calibrated on the actual Judge0 deployment hardware before going live (Pain Point P2).

F2 — Subtask scoring prevents brute-force partial credit

A flat per-test scoring system allows a candidate to earn 80% by hardcoding answers for the small test cases and ignoring the actual algorithmic challenge. Subtask groups with all_or_nothing scoring block this: the "Full constraints" subtask requires every test in the group to pass, so an O(n²) solution that times out on the large inputs earns 0 for that group — not partial credit for the tests it happened to pass.

F3 — Run mode must not affect final score

Run mode (the fast feedback loop for sample tests) runs synchronously and returns inline JSON. It must write zero score-related columns. The architectural separation is absolute: Run mode uses no BullMQ, no sessions.final_score write, no dsa_test_results insert. A candidate can click Run 100 times; it has no effect on their final score.

F4 — Score must be locked at submission time

The source code snapshot must be immutable: captured in the submissions table at submit time and never modified. If a candidate finds a bug in their code after submission, they cannot change their submission retroactively. The editor's readOnly: true state must be set synchronously on the API's 202 response — not after grading completes — to prevent a race where the candidate edits code while grading is in progress.

E — Operational considerations
O1 — Test case storage strategy (inline vs S3)

Storing all test cases inline in the DB avoids S3 round-trips at grading time. But a question with 20 hidden tests where each input is a 500-element integer array at ~2KB each = 40KB per question row. This is fine. But a question with 20 tests at 50KB each = 1MB per row — PostgreSQL TOAST threshold is 2KB, meaning 99% of that row lives in the TOAST table anyway. For large inputs (>1KB per test), S3 storage is mandatory with inline metadata only.

O2 — Batch dispatch vs per-test dispatch

Per-test dispatch: 20 sequential HTTP calls to Judge0, 20 sequential polling loops = 20× the latency overhead. Batch API: 1 HTTP call to submit all 20 tests simultaneously, 1 polling loop that checks all 20 tokens together. For 20 tests with 600ms average execution time, batch mode reduces grading time from ~15 seconds to ~3 seconds. The batch API is not optional — it is the only viable design at scale.

O3 — Orphaned session recovery

A worker crash after setting status='grading' but before writing results leaves the session permanently stuck. No SSE event ever fires. The candidate stares at a loading spinner indefinitely. A scheduled cleanup job every 5 minutes detects sessions stuck in grading for more than 5 minutes and re-enqueues the grading job. The worker's idempotency guard handles partial results correctly on retry.

O4 — Judge0 token audit trail

Every dsa_test_results row stores the Judge0 token that produced it. If a candidate disputes a verdict — "my solution was correct, the system is wrong" — the support team can use the token to re-fetch the full Judge0 result (stdout, stderr, actual time, memory) without re-running the code. This is the only forensic tool available after a grading run completes.

03 // PIPELINE WALKTHROUGH

From candidate click to score — every step explained

The DSA pipeline has two distinct modes that share infrastructure but diverge sharply in execution path, guarantees, and latency. Understanding why they are architecturally separate — not just operationally different — is essential to correctly implementing them.

WHY TWO MODES?

Candidates need fast feedback during development (Run) and authoritative grading at submit time (Submit). Merging these into one path forces a choice: either the developer loop is slow (30s per click), or the graded path doesn't have full test coverage. Two separate paths with explicit contracts solves this.

RUN MODE CONTRACT

Fast (under 10 seconds). Sample tests only. No BullMQ involvement. Synchronous response. No score writes. No DB writes to scoring columns. Result is ephemeral — lives only in the HTTP response.

SUBMIT MODE CONTRACT

Authoritative. All tests. Queued async. Score is permanent. SSE progress. Idempotent on retry. Source code snapshot is immutable. Session locked from further edits immediately on submission.

Run mode — detailed step-by-step reasoning
RUN 01
Candidate clicks Run
WHAT

POST /sessions/{id}/run with source_code + judge0_language_id in body.

WHY

Session ID in the URL (not body) lets the API verify the session belongs to the authenticated candidate without parsing the body first. The language ID in the body allows different run attempts in different languages without creating a new session.

RUN 02
API validation
WHAT

Check session.status = 'active'. Enforce code size cap (50KB). Enforce per-session rate limit (e.g., 10 runs/minute). No queue involved.

WHY

If status != 'active', the session is expired, submitted, or already grading — running code is meaningless. Size cap prevents memory exhaustion during parsing. Rate limit prevents the Run endpoint from being used to overwhelm Judge0 during concurrent exam windows.

RUN 03
Fetch sample tests + Code Merge
WHAT

SELECT * FROM dsa_test_cases WHERE question_id = $q AND is_sample = TRUE. Then merge candidate code with hidden driver per language strategy.

WHY

Only sample tests — never hidden tests — are run in Run mode. Exposing hidden test execution in Run mode would let the candidate probe whether their specific outputs match the hidden expected outputs, effectively revealing the hidden test cases through a timing/boolean oracle.

RISK

The merged code is built in memory on the API server and sent directly to Judge0 — never written to disk, never logged with driver content visible.

RUN 04–06
Dispatch → Poll → Compare
WHAT

Batch submit sample tests only. Poll every 400ms, max 10 attempts (8s timeout). Normalise and compare output server-side.

WHY

Shorter polling timeout (8s vs 30s for Submit) is acceptable because sample tests have small inputs and should complete in under 2s. The inline response pattern requires a bounded wait — we can't stream partial results back in a synchronous HTTP response.

RUN 07
Return inline JSON
WHAT

HTTP 200 with a JSON array: one verdict object per sample test. For WA, include actual vs expected diff (safe since these are sample tests, not hidden). No DB write to final_score.

WHY

Showing the diff on sample tests is intentional — the candidate needs feedback to improve. Showing it on hidden tests would expose confidential test data. The is_sample flag controls which category each test falls into.

Submit mode — detailed step-by-step reasoning
SUB 01
Candidate submits
WHAT

POST /sessions/{id}/submit with source_code + judge0_language_id.

WHY

Same endpoint structure as Run but different path suffix. The submit path carries finality — it locks the session, creates an immutable record, and begins grading. Separating it from Run prevents an accidental run from triggering a graded submission.

SUB 02
API persists + enqueues
WHAT

In a single transaction: INSERT INTO submissions (immutable snapshot). Enqueue BullMQ DSA_GRADE job with submission ID. Return 202 Accepted.

WHY

Transaction ensures the submission row and the queue job are consistent — you can't have a job with no submission row (worker would fail to find data) or a submission row with no job (candidate waits forever). The BullMQ job payload contains only the submission ID, not the source code — the worker fetches from DB to ensure it's always working with the persisted, immutable snapshot.

SUB 03
Lock session
WHAT

UPDATE sessions SET status='submitted', submitted_at=NOW() WHERE id=$id AND status='active'. The front-end receives the 202 and immediately sets Monaco to readOnly: true.

WHY

The WHERE clause on status='active' is an optimistic lock — if the session was already submitted by a concurrent duplicate request, this UPDATE silently affects 0 rows. The front-end's readOnly transition should happen on the 202 response, not after grading, because there's a window between submission and grading completion where the editor would be editable.

RISK

Network latency between the server setting submitted and the front-end receiving the response could allow an edit. The solution is to also check session status server-side on every Run request — if status is not 'active', reject the run.

SUB 04
Worker picks up — idempotency + setup
WHAT

Worker dequeues job. Check session status: if grading or complete, exit (idempotency guard). Atomically set status to 'grading'. Fetch question, language stub (starter_code + hidden_driver), and all test cases (inline + S3).

WHY

Status must be set to grading before any Judge0 calls. If the worker dispatches to Judge0 and then crashes before setting the status, the orphaned session cleanup job will retry. But the session is still in submitted status — so the retry correctly re-dispatches. If status were set after dispatch, the cleanup job can't distinguish "crashed before dispatch" from "crashed after dispatch, results already in Judge0".

SUB 05
Code Merger
WHAT

Per-language strategy merge. Merged code lives only in worker memory. Never written to disk, never logged with driver visible, never returned to the API.

WHY

The merged code contains the hidden driver. If it were logged, it would be in application logs accessible to developers, potentially violating question confidentiality. If written to disk, it persists after the job completes — a security liability. In-memory only means it lives for the duration of the job and is garbage collected immediately after.

SUB 06
Judge0 batch dispatch
WHAT

Chunk test cases into batches of max 20 (P9). Submit each chunk. Receive token arrays. All payloads use: expected_output: null, enable_network: false, cpu_time_limit = base × multiplier.

WHY

Batch size limit exists in Judge0 deployments (typically 20–50 depending on config). Chunking is defensive programming — a question might have 30 tests. Setting expected_output: null opts out of Judge0's built-in comparison, forcing the worker to do its own (correct) normalised comparison. enable_network: false is explicitly set per call, not assumed from Judge0 defaults.

SUB 07
Poll + parse all verdicts
WHAT

Exponential backoff polling across all token chunks. On each poll cycle, check for CE (halt all immediately). For completed tokens, normalise output and compare. Classify each into one of 8 verdicts.

WHY

Polling, not webhooks, because Judge0's open-source deployment doesn't support outbound webhooks. The exponential backoff is to avoid polling thrashing under load. Checking for CE on every poll cycle (not just the first) handles the race condition where CE arrives on a later poll after other tests have completed normally.

SUB 08
Score + SSE + write
WHAT

Compute subtask group scores. Idempotent upsert to dsa_test_results per test. Write final score and breakdown to sessions. Set status to 'complete'. Publish GRADING_COMPLETE event to Redis pub/sub → SSE handler → candidate browser.

WHY

Write order matters: test results first, then session status + final score. This ordering means that if the worker crashes between writing test results and updating the session, a retry can skip already-written test results (idempotency check per row) and still correctly complete the session update. The reverse order (session first) would produce a complete session with missing test result rows.

⚠

The single most important ordering invariant in the entire pipeline: status → grading BEFORE Judge0 dispatch. Results written BEFORE status → complete. These two orderings make the pipeline safe under crash + retry at any point.

04 // SCHEMA

Database schema — design decisions behind every column

The schema is not just a data model — it encodes invariants, access patterns, and business rules. Every column choice has a reason. This section explains not just what the schema is, but why each design decision was made.

Read domain vs. write domain separation

The evaluation module reads from tables owned by the question authoring module (questions, dsa_language_stubs, dsa_test_cases, dsa_subtasks) and writes exclusively to its own tables (sessions, submissions, dsa_test_results). This is a deliberate boundary: the evaluation module cannot modify a question's test cases, cannot alter time limits, and cannot change the expected output. It only records what happened when it ran the code. This separation prevents subtle bugs where a grading operation inadvertently modifies the source of truth it's supposed to evaluate against.

Why UUID for sessions.id?

A SERIAL integer ID is enumerable — a candidate can guess adjacent session IDs (e.g., their session is 10042, they try 10041 and 10043). A UUID is 128-bit random — not guessable. This prevents a class of IDOR (Insecure Direct Object Reference) vulnerabilities where a candidate fetches another candidate's results by incrementing the ID.

Why score_breakdown JSONB on sessions?

The authoritative per-test scores live in dsa_test_results.points_awarded. The JSONB snapshot on sessions is a denormalisation for read speed. The score card UI needs all test verdicts, points, and timing on page load. Without the JSONB, every score card render requires a JOIN across potentially 20+ test result rows — for a concurrent exam with 500 candidates, that's 10,000 row reads at page load time. The JSONB is written once at grading completion and read many times.

Why store stdout_actual only for sample tests?

Storing the actual stdout for hidden tests would be equivalent to revealing what the candidate's code produced on those inputs. Combined with the expected output, this would leak the hidden test data progressively. For sample tests, storing actual output is fine (the input is public) and necessary to show the diff in the UI when a candidate's answer is wrong.

Why is source_code in submissions (not sessions)?

Keeping source code in a separate submissions table with a UNIQUE(session_id, attempt_number) constraint serves two purposes: (1) idempotency — the UNIQUE constraint prevents duplicate rows on worker retry; (2) potential multi-attempt support — future extensions could allow re-submission (with scoring logic taking the best attempt). Embedding source_code directly in sessions would make either of these harder to reason about.

05 // CODE MERGER

Per-language merge strategies — why a simple concat fails

The Code Merger is the most language-sensitive component in the pipeline. It has one job: combine the candidate's solution with the hidden driver into a single runnable program. But "combine" means something different in every language. This section explains the structural reason for each merge strategy.

The fundamental problem: language file structure is not uniform

In Python, a file is a sequence of top-level statements and definitions — you can append anything after the class and it executes in order. In C++, the preprocessor must process #include directives before the compiler sees the rest of the file — you cannot have includes after function definitions. In Java, a file can have multiple class definitions but only one public class — and they must be in a specific order for some compilers. In JavaScript (Node), module exports and globals have different semantics depending on whether you're in CommonJS or ESM mode.

A string concatenation that works for Python silently breaks every other language.

Per-language strategy rationale
PY
Python — append strategy
WHY APPEND WORKS

Python files are executed top-to-bottom. A class definition before line 10 is in scope for code at line 50. Appending the driver after the Solution class works because by the time the driver code runs, the class is already defined in the module's local scope. There are no include/import ordering constraints.

EDGE CASE

If the candidate adds if __name__ == "__main__": in their starter code (trying to test locally), it will conflict with the driver's entry point. The merger should check for this pattern and strip it from candidate code before appending.

C++
C++ — inject strategy (prepend + append)
WHY INJECT IS REQUIRED

C++ compilation is a two-phase process: the preprocessor first resolves #include directives (which expand to entire header files), then the compiler sees the resulting translation unit. If you append #include <bits/stdc++.h> after the Solution class, the preprocessor processes it after the class definition, but the standard library types used in the class were never declared. Result: compilation fails with "vector undeclared".

The driver must PREPEND includes and APPEND the main() function. The candidate's code sits in the middle with access to all headers defined above it.

EDGE CASE

If the candidate puts their own includes in the starter code (which they may do locally), they may conflict with the driver's includes (duplicate symbol errors). The merger strategy for C++ should either strip known-duplicate includes or use an include guard convention.

Java
Java — same-class strategy
WHY A SEPARATE CLASS IS NEEDED

Java's entry point must be a static void main method, but it can be in any class — it doesn't have to be in the Solution class. The driver adds a separate Main class with the main method. This is possible because Java allows multiple class definitions in a single file, as long as only one is public. The candidate's Solution class (not public) and the driver's Main class (not public, but contains main) coexist in the same file.

EDGE CASE

If the candidate declares their class as public class Solution, and the file isn't named Solution.java, some Java compilers reject it. The merger must either rename the file or ensure the class declaration doesn't have the public modifier.

JS
JavaScript (Node) — module strategy
WHY MODULE APPROACH

Node.js files execute top-to-bottom. A function defined at the top level is available to code defined later. The driver appended below the candidate's function has access to twoSum because it's in the same module scope. The driver uses require('fs').readFileSync('/dev/stdin') to read all stdin at once, which is more reliable than async readline for competitive programming I/O patterns.

EDGE CASE

If the candidate uses ES Module syntax (import/export) instead of CommonJS, the driver's require() call will fail. The merger should detect ES module syntax and either reject it or wrap it appropriately.

⚠

The merger strategy map is a required data structure, not an implementation detail. Build it as { language_id: MergeStrategy } where each strategy implements merge(starterCode, hiddenDriver): string. A missing strategy must throw an explicit error. When a new language is added, a new strategy must be registered before that language can be enabled for a question. The admin panel should validate that all enabled languages for a question have a registered strategy before publication.

06 // EXECUTION

Judge0 dispatch, polling, and resource limits — the mechanics

This section covers the exact Judge0 API contract — why each field in the batch payload is set the way it is, how resource limits are calculated with language multipliers, and the mathematical reasoning behind the exponential backoff polling design.

Why each batch payload field is set the way it is
source_code
Base64 encoded
WHY

The Judge0 API transmits source code as JSON. JSON strings cannot contain raw null bytes, certain control characters, or arbitrary binary sequences. Base64 encoding ensures the source code (which may contain string literals with any character) is safely representable as a JSON string. This is a requirement of the Judge0 API, not an optional optimisation.

expected_output
Always null
WHY NULL

If you set expected_output, Judge0 performs a raw byte comparison between actual stdout and expected. This fails for: trailing whitespace on any line, Windows \r\n from Java on Windows, float outputs that differ only after the 6th decimal place, case differences when the problem is case-insensitive. The worker does its own normalised comparison. Setting expected_output: null tells Judge0 to not compare — it just returns the stdout and we compare ourselves.

enable_network
Always false
WHY EXPLICITLY FALSE

This is set explicitly per call, not assumed from Judge0 server defaults. If the Judge0 deployment has a misconfigured default (ALLOW_ENABLE_NETWORK=true), explicit false in the payload overrides it. Defense in depth: we don't trust server defaults to protect us. A candidate with network access could exfiltrate test data via outbound HTTP to a server they control.

cpu_time_limit
base × language multiplier
WHY MULTIPLY

Judge0 measures CPU time, not wall time. CPU time for Python is typically 3–5× higher than C++ for the same algorithm because CPython has a much higher constant factor per operation. Without a multiplier, every Python solution that would pass in C++ times out — this is a systematic fairness violation. The multiplier corrects for interpreter/JVM/runtime overhead, making the effective difficulty equivalent across languages.

CALIBRATION REQUIRED

The multipliers (Python 3.0×, Node 2.5×, Java 1.5×) are estimates. They must be empirically calibrated on the actual Judge0 deployment hardware before going live. See Pain Point P2.

redirect_stderr_to_stdout
Always false
WHY KEEP SEPARATE

Judge0 returns both stdout and stderr separately. Merging them (redirect_stderr_to_stdout=true) would pollute the stdout comparison — a debug print statement going to stderr would accidentally appear in the comparison output, causing spurious WA verdicts. Keeping them separate means we compare stdout only, and stderr is available for debugging (RE messages, CE output).

Exponential backoff polling — the math
Why exponential backoff? Why these specific numbers?

The goal is to detect completion as quickly as possible (minimise latency) while not overwhelming Judge0 with polling requests (minimise load). A fixed interval of 400ms is a reasonable starting point for quick tests, but under load, a fixed interval means N workers × constant request rate = linear load growth. Exponential backoff keeps early polls fast but spreads out later polls, reducing load during congested periods.

400ms initial delay: Fast tests (simple arrays, basic loops) finish in 100–300ms. Polling before 400ms guarantees a miss and wastes a request. Starting at 400ms catches fast tests on the first or second poll.

1.5× multiplier: Gentler than 2× — the sequence is 400, 600, 900, 1350, 2000 (capped). The cap at 2000ms ensures we never wait more than 2 seconds between polls even for very slow tests.

30 second hard timeout: The longest legitimate execution is base_limit × max_multiplier = 5s × 3.0 = 15s. Adding Judge0 queue time (typically 1–3s under normal load) gives a realistic worst case of ~18s. 30s provides a safety margin while ensuring orphaned jobs eventually fail rather than blocking the worker forever.

07 // SCORING

Subtask scoring + output normalisation — the complete design

Two components drive scoring: the subtask group evaluator (decides how many points each test group awards) and the output normalisation chain (decides whether a test's output is correct). Both are deterministic and must produce identical results on retry.

Why two scoring policies?
per_test — awards points for each passing test independently

Used for sample/basic constraint subtasks. A candidate gets credit for every test they pass, even if they don't pass all of them. This provides granular partial credit on the easy cases and gives good feedback: "you passed 2 of 3 basic tests".

When to use: Subtask 0 (n ≤ 10, brute force acceptable). Any subtask where partial progress is meaningful and should be rewarded.

Brute-force risk: A candidate can write O(n²) or even O(2^n) code and still pass all per_test cases if the inputs are small enough. This is intentional for Subtask 0 — we want to reward correct algorithm logic even if it's not optimal.

all_or_nothing — awards group points only if every test in the group passes

Used for high-constraint subtasks that test algorithmic complexity. If a single test in the group fails (WA, TLE, RE, MLE), the entire group awards 0 points. This forces the candidate to have a correct AND efficient solution.

When to use: Subtask 1 (n ≤ 1,000), Subtask 2 (n ≤ 100,000). Any subtask where a partial solution getting partial credit would misrepresent the candidate's algorithmic ability.

Key property: A solution that barely passes 90% of the hidden tests (gets lucky on 9/10) gets 0 points for the group — not 90%. This is correct — the solution is not reliably correct.

Output normalisation chain — every step explained
1
Normalize Windows line endings → Unix
Java on Windows, certain text editors, and some online IDEs emit \r\n (CRLF) instead of \n (LF). A raw string comparison would fail between a correct Java solution and expected output stored with LF endings. This must be the first step so subsequent operations work on a consistent line separator.
Before: "2 3\r\n5 7\r\n" → After: "2 3\n5 7\n"
2
Strip outer whitespace (trim)
Most programming languages' print functions add a trailing newline. Python's print() always adds \n. Java's System.out.println() always adds \n. The expected output stored in the DB may or may not have a trailing newline depending on how the problem author entered it. Stripping outer whitespace from both sides makes the comparison blind to this inconsistency.
Before: " 42\n " → After: "42"
3
Strip trailing whitespace per line
Some print functions add a trailing space after each number (e.g., cout << x << " " in a loop that doesn't have a special case for the last element). This is semantically correct output but fails a raw comparison against expected output without trailing spaces. Trimming each line's right side makes comparison robust to trailing spaces — a candidate shouldn't be penalised for adding a trailing space after their last output element.
Before: "1 2 3 \n4 5 6 " → After: "1 2 3\n4 5 6"
4
Collapse excessive blank lines (3+ → max 1)
Some solutions emit extra blank lines between outputs when iterating over test cases or printing debug information. Collapsing 3+ consecutive blank lines to 1 prevents spurious failures when the problem author's expected output has a slightly different blank line count. A single blank line as a separator between output groups is legitimate and preserved.
Before: "3\n\n\n\n7" → After: "3\n\n7"
5
Optional: case-insensitive comparison
Some problems ask for outputs like "YES"/"NO" or "True"/"False" where case convention differs by language (Python's True vs JavaScript's true vs Java's "true"). The case_insensitive flag on the question config allows the problem author to mark the problem as case-insensitive. Applied only when explicitly enabled — not as a default — to avoid masking real case errors in string output problems.
With flag: "True" === "true" === "TRUE" → all compare as equal
6
Float epsilon comparison (when output_type = 'float')
Floating-point arithmetic is not exact. A correct geometric algorithm may produce 0.999999999 for a result that should be exactly 1.0, due to accumulation of IEEE 754 rounding errors. A string comparison would fail. The epsilon comparison: |actual - expected| < ε. Default ε = 1e-6, but configurable per question (geometry problems may need 1e-9, approximate algorithms may accept 1e-4). See Pain Point P8 for the missing per-question epsilon config.
|0.999999 - 1.0| = 1e-6 < ε → PASS (for ε = 1e-5)

8 verdicts — complete decision logic and candidate impact

Every Judge0 status maps to exactly one verdict in our system. Every verdict has a defined worker action, a halt decision, a candidate message, and a UI behaviour. Incomplete handling of any verdict leaves the session permanently stuck in grading state.

The fundamental verdict classification

09 // REAL-TIME FEEDBACK

SSE architecture — why SSE, how it works, and what can go wrong

The real-time feedback system bridges the async grading pipeline and the candidate's browser. Understanding the full SSE lifecycle — including failure modes — is essential because a broken SSE path leaves the candidate staring at a spinner with no way to know their score is ready.

WHY SSE OVER WEBSOCKET?

SSE is unidirectional server-to-client. The candidate never needs to send messages after submission — they only receive updates. WebSocket is bidirectional (full-duplex), which is unnecessary overhead. SSE is simpler to implement, has native browser support via EventSource, works over HTTP/2 multiplexing, and automatically retries broken connections. WebSocket requires a separate upgrade handshake and doesn't auto-retry.

WHY SSE OVER POLLING?

Client polling (candidate's browser calls GET /sessions/{id} every second) would require N candidates × N requests/second = O(N²) load on the API as exam size grows. SSE is a single long-lived connection per candidate. The server pushes updates only when they're ready — zero unnecessary requests. For 500 concurrent candidates, SSE is 500 persistent connections vs potentially 30,000+ polling requests per minute.

HOW THE WORKER TALKS TO SSE

The grading worker and the SSE HTTP handler are different processes. They communicate via Redis pub/sub. The worker publishes events to a channel keyed by session ID (session:{id}). The SSE handler (running in the API server) is subscribed to that channel and forwards events to the browser connection. Redis pub/sub is the decoupling layer.

Missed event recovery — what happens when the connection drops
MISS 01
Network drops during grading

FIX

On SSE reconnect, the client must first call GET /sessions/{id}. If the response contains status: 'complete', render the score card from the REST response body — don't wait for SSE. The REST response includes the same data as the GRADING_COMPLETE event payload.

Same as above, but the network drops and recovers before grading completes. The session status is still grading.

On SSE reconnect: call GET /sessions/{id}. Status is grading — reopen the SSE connection and wait. But: the worker must be able to re-emit GRADING_PROGRESS events for already-completed tests on reconnect. This requires storing completed test verdicts in Redis (keyed by session) so the SSE handler can replay them to a reconnecting client. This is flagged as Pain Point P7.

MISS 03
Candidate closes tab then reopens
SCENARIO

Candidate submits, closes the browser tab, and reopens it 30 seconds later (after grading is complete).

FIX

On page load, the front-end fetches GET /sessions/{id}. If status = 'complete', render the score card immediately from the REST response. Never depend on SSE alone for the final score — the REST endpoint is the persistent source of truth. SSE is just the fast-path for real-time updates during the grading window.

SSE event types and their payloads

GRADING_PROGRESS — fired by worker after each test completes. Payload: {test_index, verdict, time_ms, memory_kb, is_sample}. For hidden tests, is_sample: false tells the UI not to show expected/actual diff even if it's requested.

GRADING_COMPLETE — fired once when all tests are processed. Payload: {final_score, max_score, verdict_summary, subtask_breakdown}. This is the same data the GET /sessions/{id} REST endpoint returns.

GRADING_ERROR — fired on system failure (worker crash, Judge0 timeout). Payload: {message}. Only tells the candidate to contact support — no internal details. The worker crash is logged with full context server-side.

Redis pub/sub as the SSE bridge

The grading worker runs in a separate process from the API server. They share Redis. The worker publishes to a channel keyed by session ID: PUBLISH session:{uuid} {event_json}.

The API's SSE endpoint subscribes to that channel when the candidate connects: SUBSCRIBE session:{uuid}. When a message arrives on the channel, the API forwards it to the candidate's EventSource stream.

This pattern means the API server holds one Redis subscription per active grading session. At 500 concurrent candidates, that's 500 Redis subscriptions — negligible overhead. The worker never needs to know about HTTP connections or SSE protocol.

10 // SECURITY

Judge0 hardening — threat model and defence layers

The security design is not just a checklist — it is a threat model with layers. Understanding what each control protects against makes the checklist actionable and helps detect gaps.

The attack surface: what a motivated candidate can attempt

1. Sandbox escape: Submit code that exploits a Judge0 CVE to gain access to the host filesystem. Target: other candidates' submissions, Judge0's internal database credentials, system environment variables.

2. SSRF (Server-Side Request Forgery): Submit code that makes outbound HTTP calls from inside the sandbox. Target: internal metadata services (AWS IMDS at 169.254.169.254), internal PostgreSQL, Redis, or other services on the private VPC.

3. Test case oracle: Submit code that makes outbound calls with test inputs/outputs embedded in the request. Target: reverse-engineering hidden test cases by probing system responses.

4. Resource exhaustion: Cause Judge0 or the host to run out of memory, CPU, or disk. Target: disrupting other candidates' grading during a concurrent exam.

5. Information leakage via API: Access API responses or network traffic that contains hidden test cases, expected outputs, or hidden driver code.

Defence-in-depth: three isolation rings
Ring 1 — Public Internet
Ring 2 — Internal VPC
Ring 3 — Worker Network
isolate
sandbox
Ring 1 — Public Internet → API Gateway

The only public entry point is the API Gateway on port 443 (HTTPS). Rate limiting, auth token validation, and request size limits apply here. Judge0's port 2358 is never reachable from the public internet — it binds to 127.0.0.1 only.

Ring 2 — Internal VPC → Grading Worker only reaches Judge0

Within the VPC, the grading worker can reach Judge0. But Judge0 cannot initiate outbound connections — it's a passive API server. The candidate's code inside Judge0 cannot reach the VPC network because enable_network: false disables the container's network namespace entirely.

Ring 3 — isolate sandbox (per submission)

Judge0 uses the isolate library which creates a separate Linux namespace per submission: separate PID namespace (no kill to other processes), separate network namespace (no outbound connections), separate filesystem namespace, cgroup limits on CPU and memory. Each submission is a hermetically sealed environment destroyed immediately after execution completes.

Changed passwords: Judge0's default PostgreSQL and Redis passwords are documented publicly. Any internal network attacker (or escaped sandbox) could connect to these services using the default credentials if they're not changed.

11 // OPEN PAIN POINTS

What still needs thinking — deep analysis of each gap

These are the areas where the design is incomplete, has unresolved trade-offs, or requires explicit decisions before implementation. Each pain point includes the root cause, the failure mode if ignored, and the resolution path. Severity: Critical blocks the build, High blocks production, Medium can defer to iteration 2.

CRITICAL   P1 — Driver correctness is entirely the author's responsibility

Root cause: The hidden driver for each language is manually authored and stored in dsa_language_stubs.hidden_driver. There is no automated testing, no validation gate, and no feedback loop between authoring and grading correctness.

Failure mode: A bug in the Python driver's input parsing (e.g., reading a space-separated integer list as a single string instead of parsing it) causes every Python submission for that question to get WA, regardless of how correct the candidate's algorithm is. The candidate has no way to distinguish "my code is wrong" from "the platform is broken". The author has no way to detect this until complaints arrive.

Resolution:

  • Build a driver validation tool in the admin panel: author enters a known-correct reference solution, runs it through the full merge + dispatch cycle for each enabled language, verifies AC on all sample tests.
  • Gate the question's PUBLISHED status: requires at least one successful reference run per enabled language. No publication without validation.
  • The reference solution + expected output is stored, enabling regression testing if the driver is later modified.
CRITICAL   P2 — Time multiplier values are not empirically calibrated

Root cause: The multipliers (Python 3.0×, Node 2.5×, Java 1.5×) are reasonable estimates based on general knowledge, not measurements on the specific Judge0 deployment.

Failure mode: On ARM hardware (where Python's gap over C++ is smaller), Python 3.0× is too lenient, accepting O(n²) solutions that should TLE. On slow shared instances, Java 1.5× is too tight, causing TLE for correct O(n log n) solutions due to JVM startup overhead. Both are systematic fairness violations affecting an entire language's candidates.

Resolution:

  • Before go-live: run a benchmark suite (5–10 standard algorithms: sorting, BFS, DP, string matching, binary search) in every supported language against the actual Judge0 cluster.
  • Measure execution times at P50, P95, P99 across 20 runs each.
  • Set multipliers to the P95 ratio relative to the C++ baseline: if Python P95 is 4.2× C++ P95, set Python multiplier to 4.2.
  • Make multipliers configurable per-deployment via environment variable, not hardcoded per question.
CRITICAL   P3 — CE halt has a race condition in batch mode

Root cause: The CE halt logic was designed for sequential dispatch (detect CE on test 1, don't dispatch test 2). But the design uses batch dispatch — all tests are submitted simultaneously before any results arrive.

Failure mode: All 20 tests execute in Judge0 even when the code has a compile error. 19 Judge0 execution slots are consumed unnecessarily. Under load, this delays other candidates' submissions. The slots are wasted but the verdict is still correct — all 20 return CE.

Resolution (short-term): Accept the wasted slots. On detecting CE in any result during polling, immediately mark all remaining results as CE and close the session. Do not wait for the other tokens to complete.

Resolution (long-term): Implement a pre-compile step — submit a compilation-only token (no stdin, no test input) first, wait for it, and only proceed to full batch dispatch if it returns status 3 (OK, code compiled successfully). This adds ~500ms to the happy path but eliminates 100% of wasted batch slots on CE.

HIGH   P4 — Orphaned session recovery is not fully designed

Root cause: The cleanup job is mentioned but its exact behaviour is unspecified. Specifically: what to do with partial results (some dsa_test_results rows may already exist), how many retries before giving up, and what state to set on permanent failure.

Failure mode: A worker crashes after writing 10 of 20 test results. The cleanup job retries. But the retry doesn't know to skip the 10 already-written results — it may double-insert them, corrupting the score. Or it may overwrite them with correct values if the idempotency check is per-row. Without a clear spec, the retry logic is likely implemented incorrectly on the first attempt.

Resolution:

  • Per-row idempotency: before inserting a dsa_test_results row, check WHERE session_id=$s AND test_case_id=$t — skip if already exists.
  • After 3 retries (configured), set session status to 'failed' and publish GRADING_ERROR to the SSE channel.
  • The cleanup job query: SELECT id FROM sessions WHERE status='grading' AND updated_at < NOW() - INTERVAL '5 minutes'. Enqueue a retry job for each found session.
HIGH   P5 — Large test case S3 latency adds to grading time

Root cause: No caching strategy is defined for test case content. Every grading run for a question with S3-stored test cases makes N sequential S3 GET requests.

Failure mode: For a question with 20 S3 test cases, each at ~50KB, a cold start adds 20 × 40ms (S3 GET latency in same region) = 800ms before any Judge0 dispatch begins. During a peak exam window where 100 candidates all submit the same question simultaneously, this creates 2,000 S3 GETs in a few seconds — a potential S3 rate limit event.

Resolution: Prefetch and cache all test case content for a question on first access. Cache key: tc:{question_id}:{test_index} in Redis with 5-minute TTL. Subsequent submissions for the same question in the same exam window hit Redis instead of S3.

HIGH   P6 — No plagiarism or code similarity detection

Root cause: No mechanism exists to detect two candidates submitting identical or near-identical code.

Failure mode: Two candidates share solutions — both score full marks. In a competitive exam context, this is a hiring integrity issue. Without detection, it goes unnoticed.

Resolution: At grading time, compute a normalised hash of the submitted source code (strip comments, normalise whitespace, lowercase) and store on the submission row. After grading, a background job queries for other sessions on the same question with a matching hash. Matches are flagged for recruiter review — not automatically penalised, since independent solutions can legitimately be similar for simple problems. For deeper analysis, consider MOSS (Measure Of Software Similarity) as a deferred phase.

HIGH   P7 — SSE missed-event scenario not fully handled

Root cause: Redis pub/sub is fire-and-forget. If no subscriber is listening when a GRADING_COMPLETE event is published, the event is permanently lost. The design mentions a REST fallback but the exact client reconciliation logic is not specified.

Failure mode: A candidate's network drops for 5 seconds during grading. GRADING_COMPLETE fires during the outage. Network recovers. Browser reconnects SSE. No event is ever delivered. The candidate sees a loading spinner indefinitely, score is actually in the DB. Likely perception: "the system is broken", candidate reports to support.

Resolution:

  • On SSE reconnect, client MUST call GET /sessions/{id} first. If status is 'complete', render score card from REST response immediately.
  • If status is 'grading', reopen SSE and wait. Worker must store completed test verdicts in Redis per session (as a sorted list, keyed by test index), so the SSE handler can emit replay events for already-completed tests to a reconnecting client.
  • Redis key for replay: grading_progress:{session_id} — a sorted set of completed test verdicts, with TTL of 10 minutes after grading completes.
MEDIUM   P8 — Float output comparison epsilon is not configurable per-question

Root cause: The normalisation chain uses a hardcoded 1e-6 epsilon for float comparison. No per-question configuration exists.

Failure mode: A geometry problem requiring 1e-9 precision (computing pi, Euclidean distance on large coordinates) incorrectly marks solutions as AC that have accumulated floating-point errors larger than 1e-6. A Monte Carlo approximation problem correctly uses 1e-4 precision but gets WA with a 1e-6 epsilon.

Resolution: Add float_epsilon NUMERIC and output_type VARCHAR (float | integer | string | multiline) columns to the questions table. The normalisation function reads these from question config at grading time. Default: 1e-6 for float, exact string match for all others.

MEDIUM   P9 — Judge0 batch size limit not accounted for

Root cause: Judge0's batch API has an undocumented but real limit on submissions per batch call (typically 20–50 depending on deployment configuration). A question with 30 test cases submitted in a single batch call may fail silently — Judge0 may return a 400 error or truncate the batch.

Failure mode: Silent failure — grading appears to start but only 20 of 30 tests are dispatched. The worker polls for 30 tokens but only 20 exist in Judge0. The missing 10 are never accounted for. Session may get stuck in grading or produce an incorrect partial score.

Resolution: Chunk test cases into batches of max 20 (configurable via environment variable JUDGE0_BATCH_SIZE). Poll each chunk independently using its token array. Merge all results before scoring. Chunking should be transparent to the scoring logic — it still receives a flat array of 30 test results.

MEDIUM   P10 — No run-mode rate limiting per candidate

Root cause: The Run mode endpoint has no per-session rate limit defined in the current design.

Failure mode: A candidate (or automated tool running in the background) hammers the Run button continuously, saturating Judge0's queue and delaying other candidates' Run and Submit grading. In a competitive exam with 500 candidates, one abuser can degrade the entire exam experience.

Resolution: Per-session rate limit of 10 runs/minute. Return 429 with Retry-After header when exceeded. Implement a 500ms debounce on the front-end Run button to prevent accidental rapid-fire clicks. Rate limit key: rate:run:{session_id} in Redis with 1-minute sliding window.

MEDIUM   P11 — No observability defined for the grading pipeline

Root cause: No metrics, alerting, or tracing specification exists. The grading pipeline runs as a black box.

Failure mode: Judge0 goes down. Worker queue depth grows to 1000 jobs. Candidates submit and get no feedback. No alert fires. The incident is discovered when enough candidates email support — 20 minutes later. At that point, 1000 grading jobs are stale and need reprocessing.

Resolution:

  • Prometheus metrics: queue depth (gauge), grading latency p50/p95/p99 (histogram), verdict distribution (counter), Judge0 error rate (counter).
  • Alerts: queue depth > 50 for more than 2 minutes; grading latency p95 > 30s; error rate > 5% over 5 minutes.
  • Structured logging: every worker log line must include session_id, question_id, judge0_token, and verdict for full trace reconstruction without a dedicated tracing system.
12 // BUILD PHASES

Recommended build sequence — why this order

The build sequence is designed so that each phase produces a testable deliverable and unblocks the next phase. The ordering follows the dependency graph: you can't test the worker without Judge0 running; you can't test SSE without the worker emitting events; you can't calibrate multipliers without the full grading loop working.

ℹ

Why not build everything in parallel? Schema changes made after the worker is built require worker code changes. A worker built before the Code Merger is tested will have untested language handling. SSE built before the worker emits events has no source of events to verify against. The phased sequence prevents rework by ensuring each dependency is validated before the next layer is built on top of it.

PHASE 01
Schema + Judge0 setup

What: Deploy Judge0 v1.13.1+ with all hardening flags applied. Create evaluation schema: sessions, submissions, dsa_test_results. Verify Judge0 responds correctly to a manual batch submit for Python, Java, C++.

Why first: Everything else depends on Judge0 being reachable and the schema existing. A schema migration discovered mid-development of the worker requires rebuilding the worker's data layer. Do the schema first so it's stable.

  • Deliverable: Judge0 cluster running internally with hardened config. Schema migrated. Manual curl test passes for all languages.
  • Pain points addressed: S1, S2 (security baseline established).
PHASE 02
Code Merger

What: Build the per-language strategy map. Implement and unit-test merger strategies for Python, Java, C++, JavaScript. Build a driver validation tool for the admin panel that runs a reference solution through the full merge + dispatch cycle.

Why second: The merger is the most testable component in isolation — it's a pure function of (starterCode, hiddenDriver) → mergedCode. Test it standalone before integrating it into the worker. This ensures language bugs are caught before they're buried inside a larger async system.

  • Deliverable: Merger tested for all target languages. Admin can validate drivers before publishing. Unit test suite covers all 4 language strategies and edge cases.
  • Pain point addressed: P1 (driver correctness — validation tool built).
PHASE 03
Grading worker (Submit mode)

What: Build the BullMQ grading worker: idempotency guard, fetch test cases, Code Merger invocation, batch dispatch with chunking, exponential backoff polling, 8-verdict handler including CE halt, output normalisation, subtask scoring, idempotent DB writes. No SSE yet — verify correctness via DB inspection.

Why third: The worker is the core of the pipeline. Verify it produces correct DB results before adding the SSE layer. An SSE bug and a worker bug at the same time are much harder to debug than either alone. Isolate the worker correctness verification to DB state only.

  • Deliverable: End-to-end grading works for all 8 verdicts. Scores correct in DB. Verified by direct DB query after manual submission.
  • Pain points addressed: P3 (CE halt), P4 (idempotency guard), P9 (batch chunking).
PHASE 04
Run mode + SSE

What: Add the synchronous Run endpoint (sample tests only, no queue, inline response). Add SSE endpoint and Redis pub/sub bridge. Wire the worker to emit GRADING_PROGRESS and GRADING_COMPLETE events. Implement the client-side SSE fallback to REST on reconnect.

Why fourth: SSE requires a working worker to have events to emit. Run mode shares the Code Merger and normalisation logic but uses a different dispatch path — verify it independently. The missed-event reconnect logic requires both SSE and REST to be working, so implement both in this phase.

  • Deliverable: Score card renders in real-time. Missed-event reconnect handled. Run mode returns correct inline results.
  • Pain points addressed: P7 (SSE missed events), P10 (Run mode rate limiting).
PHASE 05
Calibration + production hardening

What: Run the benchmark suite to calibrate language time multipliers empirically. Implement test case S3 caching in Redis. Add orphaned session cleanup job with retry logic. Add Prometheus metrics, alerting rules, and structured logging. Add code similarity hash at submission time.

Why last: Calibration requires the full pipeline to be working — you can't measure multipliers without grading. Observability built before the system is working measures incorrect behaviour. The cleanup job requires a working worker to have retry logic for. Phase 5 is production-readiness on top of a working system, not foundational work.

  • Deliverable: Production-ready pipeline with observability, calibrated multipliers, S3 caching, and recovery.
  • Pain points addressed: P2 (multiplier calibration), P4 (cleanup job), P5 (S3 caching), P6 (similarity hash), P11 (observability).
✓

After Phase 3, the system is functionally correct. After Phase 4, it has a good candidate experience. After Phase 5, it is production-safe. This progression allows internal testing and staged rollout — Phase 3 can be used for internal QA before Phase 4 is complete.
